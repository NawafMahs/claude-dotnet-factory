# Decision log

Status: **Accepted** = built in v0.1 · **Proposed** = open for change · **Rejected** = considered and dropped.

| # | Decision | Status | Why | Alternatives considered |
|---|---|---|---|---|
| D1 | **Hybrid topology**: a global core (two plugins) + a per-repo profile generated in each repo | Accepted | Repos differ in host (GitLab / Azure DevOps), DB (SQL Server / Postgres), tracker (Trello / Jira) and architecture (layered legacy apps vs Clean Architecture ones). Process and guardrails are the same everywhere; facts are not. | Global-only (wrong facts per repo); repo-only (copy-paste drift across repos). |
| D2 | **Knowledge stores, one kind of fact each**: repo facts → `<repo>/.factory/knowledge/` + `profile.md`; user preferences → Claude memory; team knowledge → committed `AGENTS.md`/`Docs/` only by the user's choice; Obsidian optional export | Accepted | Four overlapping stores already existed (memory, ~40 root `.md` files, graphify, Obsidian). Each fact now has one home. | Obsidian as primary (not next to the code; vault not confirmed); committing `.factory/` (team didn't ask for it). |
| D3 | `.factory/` is **git-excluded** (`.git/info/exclude`), not `.gitignore`d | Accepted | Personal state; no change to the team's repo files. | `.gitignore` entry (modifies a tracked file). Risk: lost on re-clone — acceptable for v0.1. |
| D4 | **Main session is the orchestrator**; no orchestrator agent | Accepted | Subagents start cold; an orchestrator agent would only duplicate the session. | Dedicated orchestrator agent (reference v2 uses a skill too). |
| D5 | **5 agents, not 12**: `investigator` (context isolation), `code-reviewer`, `db-reviewer`, `security-reviewer`, `ui-reviewer` (independent judgment) | Accepted | Agents earn a place only for context isolation, independent judgment or parallelism. Architect / API / Domain / Performance / DevOps / Docs roles became skill steps and review checklists. | 12 role agents (cost, hand-off loss, scope creep — matches the recorded "only what's asked" feedback). |
| D6 | **Scripts decide, agents judge**: gate (`gate.mjs`), reviewer routing (`route.mjs`) and job stage (`job.mjs`) are deterministic | Accepted | "Builds/tests pass" must come from a command, not an opinion. Routing from the diff is cheap and visible. Idea taken from zazencodes software-factory v2 (GPL-3; ideas only, no code copied). | LLM-chosen reviewers; LLM-reported test results. |
| D7 | **Guardrails as PreToolUse hooks** (deny / ask), principles as SessionStart context | Accepted | A rule in a prompt is a suggestion; a hook is enforced on every tool call, including subagents. | Prompt rules only. |
| D8 | Guard **fails open** on internal errors | Accepted | A bug in the guard must not brick every session. Principles still forbid the same actions. | Fail closed (safer, but one bad parse blocks all shell use). |
| D9 | **Two human checkpoints** per job: plan approval, delivery approval. The factory never merges | Accepted | Human oversight for risky operations; MR review stays with the team (`mtrabolsi` etc.). | Reference v2 auto-merges via an approver agent — rejected for enterprise/government repos. |
| D10 | **Delivery delegates** to existing repo skills (`create-mr`, `create-pr`), generic CLI fallback | Accepted | Don't rebuild what exists. | A new universal MR skill. |
| D11 | **Node.js** (built-ins only) for scripts | Accepted | Present on the machine (v24), cross-platform, robust JSON; avoids PowerShell quoting issues seen before. | PowerShell (quoting), Python (reference uses it; less certain on every box). |
| D12 | Packaged as a **local plugin marketplace** in its own git repo | Accepted | Versioned, installable/uninstallable in one command, namespaced (`/dotnet-factory:*`), no edits to `~/.claude/settings.json` by hand. | Loose files in `~/.claude/` (no versioning, mixed with other skills). |
| D13 | **UI factory as a second plugin** extending the first (same job folder/gate/router) | Accepted | UI work needs different discovery (design system, RTL), build rules and browser verification, but the same lifecycle. | Separate pipeline (duplication); UI rules inside dotnet-factory (noise for backend-only repos). |
| D14 | One `ui-reviewer` (visual + UX + a11y) instead of separate UI and UX reviewers | Accepted | Halves cost; one lens with a checklist is enough for admin/government back-office UIs. | Reference v2's split ux/ui reviewers. Revisit if public-facing UIs need deeper UX review. |
| D15 | Speckit stays for large, unknown-heavy features; the factory plan is for ticket-sized work | Accepted | Already installed and fits big specs; don't force everything through one tool. | Replace Speckit. |
| D16 | Cursor sharing via a committed `AGENTS.md` (Claude imports it with `@AGENTS.md`) | Proposed | One source for both tools — but it is a team-visible change, so only when the user decides. | Separate `.cursor/rules`. |
| D17 | Clean up unrelated global skills (Vercel/React…) | Proposed | Less noise in skill selection. Not done: outside this task's scope. | — |
| D19 | **Read-only local dashboard** (`dashboard.mjs`, Node `http` on 127.0.0.1:4777) over every repo in `~/.software-factory/repos.json`; columns derived from job files (`jobs.mjs` `COLUMN`) | Accepted | You see what waits on you across every repo without asking. Read-only keeps approvals in the chat, where they are recorded and the guard applies. Inspired by the reference factory's dashboard. | Writable board with approve buttons (approval outside the audited chat); per-repo static HTML (no cross-repo view). |
| D20 | **Jobs are scoped to their own changes**: `job new` records `base_commit` and the user's pre-existing uncommitted files; gate, router and reviewers diff from that commit and ignore those files | Accepted (2026-11-21) | Diffing against `origin/Development` pulled earlier branch commits and unrelated files into review, routing extra reviewers (seen on a real repo: ui-reviewer for an unrelated `.cshtml`). | Branch-base diff (over-reviews); asking the user each time. |
| D21 | **Reviewer model by risk** (`routing.json` `models`): Sonnet by default; Opus only for code review on high risk and security review on medium/high. Agents default to Sonnet; `route.mjs` prints `MODELS:` and the orchestrator passes it | Accepted (2026-11-21) | Opus on every code review was the largest per-job cost. A miss is expensive only where risk is high. | Opus always (cost); Haiku for low risk (too many misses on business rules). |
| D22 | **Lighter small-fix track**: no context/plan files, no checkpoint 1, code-reviewer only on Sonnet; quick edits asked outside the factory stay outside it | Accepted (2026-11-21) | Six cold-start stages for a 3-file fix cost more than the fix. | One pipeline for everything. |
| D23 | **Graph first, ranges only — enforced**: a `PreToolUse` Read hook denies whole-file reads of code/data files over 400 lines (configurable `max_full_read_lines` in `.factory/guard.json`); skills and agents must run graphify first and record a `## Graph` line | Accepted (2026-11-21) | A finished job never used graphify and read whole files (e.g. an 8.8k-line service). A prompt rule was ignored; a hook is not. | Prompt-only rule (was ignored). |
| D24 | **Short always-on context**: principles trimmed (~1.3 KB), profile split into `profile.md` (≤ 3 KB, read by everyone) + `profile-details.md` (on demand); replies in short Arabic | Accepted (2026-11-21) | Every session and every agent paid for a 9 KB profile and long principles; Arabic output costs roughly 2–3× English tokens per word, so replies must be brief. | English replies (user prefers Arabic). |
| D25 | **Graph hygiene**: session start warns when the graph is older than recent commits (`graphify update .` is AST-only, zero LLM tokens); vendor front-end code excluded via a git-excluded `.graphifyignore` | Accepted (2026-11-21) | A stale graph sends agents back to grep; vendor JS tripled the graph (9k → 30k nodes) and bloats every query. | Manual refresh only. |
| D18 | Issue-queue / concurrent jobs (reference v2) | Rejected for now | Work arrives as Trello/Jira tickets and conversations, one at a time; a queue adds machinery without a current need. | — |
